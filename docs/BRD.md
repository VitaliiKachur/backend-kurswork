# Business Requirements Document

## 1. Мета документа

Документ описує бізнес-потреби, цілі, ролі користувачів і вимоги до вебзастосунку інтернет-магазину "ТехОк". Система створена для продажу електротоварів та техніки через вебінтерфейс.

## 2. Бізнес-ціль проєкту

Основна бізнес-ціль - надати клієнтам зручний онлайн-канал для перегляду товарів, формування кошика та оформлення замовлень, а адміністратору - інструменти для керування асортиментом і даними магазину.

## 3. Бізнес-проблема

Без вебсистеми магазин має такі обмеження:

- клієнтам складно швидко переглядати асортимент і наявність товарів;
- оформлення замовлень потребує ручної комунікації;
- адміністратору складно централізовано підтримувати актуальні товари, категорії та залишки;
- відсутня історія замовлень для клієнта;
- немає автоматичної перевірки залишків під час оформлення покупки.

## 4. Очікувані бізнес-результати

- Зменшення часу оформлення замовлення клієнтом.
- Підвищення доступності каталогу товарів для покупців.
- Зменшення помилок під час продажу товарів, яких немає в наявності.
- Централізоване керування товарами, категоріями та замовленнями.
- Покращення клієнтського досвіду завдяки профілю, кошику та історії замовлень.

## 5. Зацікавлені сторони

| Сторона | Інтерес |
| --- | --- |
| Власник магазину | Збільшення продажів, контроль асортименту та замовлень |
| Адміністратор | Швидке додавання, редагування й видалення даних |
| Клієнт | Зручний пошук товарів, кошик, оформлення замовлення |
| Розробник | Підтримувана архітектура, зрозумілі маршрути, документація |

## 6. Обсяг проєкту

### Входить в обсяг

- Головна сторінка магазину.
- Каталог категорій.
- Перегляд товарів за категоріями.
- Пошук, фільтрація та сортування товарів.
- Детальна сторінка товару.
- Реєстрація та авторизація клієнтів.
- Особистий кабінет клієнта.
- Кошик покупок.
- Оформлення замовлення.
- Перегляд замовлень клієнта.
- Адмін-панель для керування основними таблицями.
- JSON-ендпоінти для кошика та перевірки email.

### Не входить в обсяг

- Онлайн-оплата через платіжні системи.
- Служби доставки з автоматичним розрахунком вартості.
- Email/SMS-сповіщення.
- Публічний REST API для сторонніх сервісів.
- Багатомовність.

## 8. Бізнес-правила

| ID | Правило |
| --- | --- |
| RULE-01 | Додавати товари в кошик можуть тільки авторизовані клієнти. |
| RULE-02 | Кількість товару в кошику не може перевищувати `StockQuantity`. |
| RULE-03 | Оформити замовлення можна тільки з непорожнім кошиком. |
| RULE-04 | Перед створенням замовлення система повторно перевіряє залишки товарів. |
| RULE-05 | Після успішного замовлення кошик клієнта очищається. |
| RULE-06 | Доступ до адмін-панелі має тільки користувач з `is_admin = 1`. |
| RULE-07 | Товар не можна видалити, якщо він уже використовується в замовленнях. |
| RULE-08 | Email клієнта має бути унікальним. |

## 9. Основні бізнес-процеси

### 9.1 Купівля товару клієнтом

1. Клієнт відкриває каталог або категорію.
2. Клієнт знаходить товар через перегляд, пошук або фільтри.
3. Клієнт відкриває детальну сторінку товару.
4. Клієнт додає товар у кошик.
5. Система перевіряє авторизацію та наявність товару.
6. Клієнт переходить до кошика.
7. Клієнт змінює кількість або видаляє позиції за потреби.
8. Клієнт відкриває оформлення замовлення.
9. Клієнт вводить контактні дані, адресу та метод оплати.
10. Система створює замовлення, позиції замовлення, зменшує залишки та очищає кошик.

### 9.2 Реєстрація клієнта

1. Клієнт відкриває сторінку реєстрації.
2. Клієнт вводить ім'я, прізвище, email, пароль та додаткові дані.
3. Система перевіряє обов'язкові поля.
4. Система перевіряє, що email ще не використовується.
5. Система створює нового клієнта.
6. Клієнт переходить на сторінку входу.

### 9.3 Адміністрування товарів

1. Адміністратор входить у систему.
2. Адміністратор відкриває адмін-панель.
3. Адміністратор вибирає таблицю `products` або `categories`.
4. Адміністратор додає, редагує або видаляє запис.
5. Система перевіряє права доступу та коректність даних.
6. Система зберігає зміни в базі даних.

## 10. Критерії приймання

| ID | Критерій |
| --- | --- |
| AC-01 | Гість може переглянути категорії та товари без входу. |
| AC-02 | Користувач може зареєструватися з унікальним email. |
| AC-03 | Користувач не може зареєструватися з email, який уже існує. |
| AC-04 | Авторизований клієнт може додати товар у кошик. |
| AC-05 | Система повертає JSON-відповідь після додавання товару в кошик. |
| AC-06 | Система блокує додавання товару понад доступний залишок. |
| AC-07 | Клієнт може оформити замовлення, якщо кошик не порожній. |
| AC-08 | Після оформлення замовлення залишки товарів зменшуються. |
| AC-09 | Неавторизований користувач перенаправляється на сторінку входу при доступі до кошика. |
| AC-10 | Неадміністратор не має доступу до адмін-панелі. |

## 11. Ризики

| Ризик | Вплив | Пом'якшення |
| --- | --- | --- |
| Відсутність хешування паролів | Високий ризик безпеки | Додати `password_hash` і `password_verify` |
| Залежність від сесії PHP | Потрібна коректна робота cookie | Перевіряти сесії на захищених маршрутах |
| Невідповідність залишків під час одночасних замовлень | Можливий продаж понад залишок | Використовувати транзакції та блокування рядків у БД |
| Локальна прив'язка до `/site` | Складніше розгортання в іншій директорії | Винести base URL у конфігурацію |

## 12. Метрики успіху

- Клієнт може оформити замовлення за один стандартний сценарій без ручної допомоги.
- Адміністратор може додати новий товар через адмін-панель.
- Кошик завжди показує актуальну кількість товарів.
- Система не дозволяє оформити товар у кількості, більшій за залишок.
